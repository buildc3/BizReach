# CLAUDE.md — AI Behavior Rules for the Lead-Gen App

This file governs how any AI coding assistant works in this repository. Read it before writing or changing code. It describes the stack **as it actually exists in the code** — if any doc contradicts the code, the code wins.

---

## Project Summary

A **local web app** for a marketing agency's lead generation: scrape business data by area/category (Google Places), auto-group leads by contact channel, generate per-lead outreach pitches (template merge or AI), review them, send via WhatsApp through a rate-limited queue, and track replies/follow-ups. Everything runs on the user's machine.

## Actual Tech Stack (authoritative)

Two processes, one app (migrated 2026-07-17 from a Rust/axum + Tauri stack — see `strategy.md` / `progress.md` for the migration history):

| Part | Stack | Notes |
|---|---|---|
| `next-app/` | **Next.js 16 (App Router)**, **React 19 + TypeScript 5 (strict)**, **Prisma 7** → **PostgreSQL** | Single Node server on `http://localhost:3000`. Frontend pages **and** backend API live in this one project — there is no separate backend process. DB runs in Docker container `postgres-client`. TanStack Query 5 (server state), Zustand 5 (UI-only state), Tailwind v4 (CSS-first `@theme` in `src/app/globals.css`), shadcn/ui, React Hook Form + Zod 4. |
| `sidecar/` | **Node.js (plain ESM JS)**, Express + **Baileys** | Local WhatsApp bridge on `127.0.0.1:3099` (`/api/status`, `/api/send`, `/api/logout`). Unchanged by the migration. |

Other facts:

- **AI provider is Google Gemini** (OpenAI-compatible chat completions endpoint, default model `gemini-2.5-flash`) — see `next-app/src/lib/services/pitch.ts`. Not Claude, not OpenAI.
- Scraping uses **Google Places API** (`GOOGLE_PLACES_API_KEY`).
- Secrets live in `next-app/.env` (`DATABASE_URL`, `GEMINI_API_KEY`, `GOOGLE_PLACES_API_KEY`, `SIDECAR_URL`, `JWT_SECRET`). Never hardcode, never commit.
- **The app requires login.** Email/password auth (JWT httpOnly cookie, `next-app/src/lib/auth.ts`), every resource (`Search`/`Product`/`Template`/`Lead`/`SenderProfile`) scoped to the signed-in user, `Group`/`Message` scoped transitively via their parent. Every `/api/v1/*` route handler starts with `const userId = await requireUser(req)`, and every `lib/repo/*.ts` function takes `userId` and filters by it — see `.ai/patterns.md` §12 before adding a new endpoint or repo function.
- Start everything with `./start.ps1` (sidecar `node index.js`, app `npm run dev`).
- Do **not** introduce alternative libraries (Redux, MUI, Axios, styled-components, ESLint plugins, etc.) without explicit approval.
- **This Next.js version has real breaking changes vs. older training data** (e.g. route/page `params` is a `Promise` that must be `await`ed, Prisma 7 requires a driver adapter). Before writing App Router or Prisma code, check `next-app/node_modules/next/dist/docs/` or the installed package docs rather than assuming an older API shape. `next-app/AGENTS.md` carries this same warning.
- `backend/` and `lead-gen-app/` (the old Rust/Tauri stack) may still be present on disk during the soak period after migration — they are **not** part of the running app. Don't add code there. If they're gone, this note is stale; ignore it.

## The Prisma / Next.js Workflow (read before any DB change)

Prisma replaces the old sqlx compile-time-against-live-DB coupling — there is no equivalent gotcha, but the workflow is still specific:

1. Edit `next-app/prisma/schema.prisma`.
2. Generate a migration: `npx prisma migrate dev --name <description>` (run from `next-app/`) — this applies the migration to the Docker DB **and** regenerates the client in one step during local dev.
3. `npx prisma generate` if you only changed the client config (rare).
4. Update `next-app/src/lib/repo/*.ts` (the only place Prisma calls live) and `next-app/src/lib/schemas.ts` (zod — **DB `CHECK` constraints are not enforced by Prisma Client**, so any status/enum-like column needs its own zod validation in the route handler, mirroring the constraint).
5. Restart `next dev` is usually not required (hot reload), but do it if behavior looks stale.

`next-app/src/generated/prisma/` is generated code — never hand-edit it, it's gitignored and gets regenerated by `prisma generate`.

## Required Workflow (mandatory, every task)

**Before writing any code:**

1. **Read the relevant `.ai/` docs**: `.ai/architecture.md` (where code belongs), `.ai/patterns.md` (the established way), `.ai/coding-standards.md`. For UI work also `.ai/design.md`. For context on the current initiative, `.ai/project.md`.
2. **Search for similar existing code** in the repo and reuse its shape — don't invent a parallel approach.
3. **Provide a requirement analysis**, explicitly covering these hidden requirements:
   - **Permission** — who/what may perform this action? (local single-user app, but e.g. only `reviewed` pitches may be sent)
   - **Duplicate** — what happens if this runs twice? (re-scrapes, re-generation, double-enqueue, migration re-runs)
   - **Failure** — partial failure behavior (Gemini call fails mid-batch, sidecar down, DB error mid-loop)
   - **Concurrency** — background tasks (fire-and-forget async work, the send-queue worker) racing with user actions; also Next.js dev-mode hot-reload duplicating in-process singletons (see the `globalThis` guard pattern in `lib/db.ts` and `lib/services/send-queue.ts`)
   - **Audit** — status/timestamp trail (`sentAt`, `reviewedAt`, `deliveredAt`, console/log lines)
4. **Present an implementation plan** (files to touch, order, migration needs).
5. **STOP and wait for explicit approval.** Do not write code before the user approves the plan.

**After approval:**

6. Implement **only what was approved** — no scope creep.
7. Review the diff against `.ai/review-rules.md` and state the result.
8. Run the **update-patterns** skill (`.claude/skills/update-patterns/`): if the change introduced a new reusable pattern, propose adding it to `.ai/patterns.md` and wait for approval before writing it.

If a request conflicts with the architecture or patterns docs, **stop and flag it** rather than silently diverging.

## Core Rules

- **Business logic lives in `next-app/src/lib/`** (`repo/` for Prisma queries, `services/` for external I/O). Route handlers (`app/api/v1/**/route.ts`) validate input and orchestrate — no Prisma calls, no `fetch` to external APIs directly in a route handler. Pages/components render, validate forms, and call hooks — nothing more.
- **Never trust the frontend.** Validate all inputs inside route handlers (zod, `lib/schemas.ts`) even though the UI also validates with Zod (`lib/form-schemas.ts`) — these are two different schema files for two different trust boundaries, don't conflate them.
- **Server data flows one way:** route handler → `src/lib/api.ts` → TanStack Query hook → component. Never cache server data in Zustand.
- **Errors are typed.** Route handlers throw `AppError` (`lib/errors.ts`) or let zod/Prisma errors propagate through `withRoute()`; responses use the `{ success, code, message }` envelope; the frontend surfaces errors via TanStack Query error states — never silent `catch {}`.
- **All WhatsApp sends go through the rate-limited queue** (`lib/services/send-queue.ts`). Never loop-and-send directly — the WhatsApp number gets banned.
- **Schema changes go through Prisma Migrate** (`next-app/prisma/schema.prisma` + `prisma migrate dev`) — never ad-hoc DDL left unrecorded.
- **Match surrounding style.** Small, reviewable diffs over rewrites.
